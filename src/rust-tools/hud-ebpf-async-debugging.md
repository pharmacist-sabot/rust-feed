# แก้ปัญหาระบบ Async อืดแบบไม่ต้องแก้โค้ดด้วย hud และ eBPF

> 📅 วันที่เผยแพร่: 2026-01-24

ปัญหาคลาสสิกที่ชาว Rustacean สาย Backend มักเจอเมื่อทำระบบ High-concurrency คืออาการที่ Latency พุ่งสูงขึ้นเวลามีโหลดเข้ามาเยอะๆ ทั้งที่ CPU ก็ไม่ได้ทำงานหนักจนเต็ม 100% และใน Log ก็ไม่มี Error หรือ Panic อะไรแจ้งเตือนเลย อาการ "เงียบแต่หน่วง" แบบนี้ มักมีสาเหตุมาจากสิ่งที่เรียกว่า Blocking Code ที่แฝงตัวอยู่ใน Async Runtime ซึ่งเป็นจุดตายที่หาเจอได้ยากมากหากไม่มีเครื่องมือที่เหมาะสม

เพราะโดยธรรมชาติของ Tokio นั้นใช้การทำงานแบบ Cooperative Scheduling ที่ Worker Thread จะสลับกันทำงาน แต่ถ้ามี Task ไหนเผลอไปทำงานหนักๆ อย่างเช่นการ Hash Password หรือการอ่านไฟล์ขนาดใหญ่โดยไม่คืนสิทธิ์การทำงาน Thread นั้นก็จะถูกยึดครองไปจนหมด ส่งผลให้ Task อื่นๆ ที่รอคิวอยู่เป็นร้อยเป็นพันต้องหยุดชะงักตามไปด้วย

ปกติแล้วถ้าเราจะล่าตัวการที่ทำให้เกิดอาการนี้ เราอาจต้องรื้อโค้ดเพื่อฝังเครื่องมือวัดผล หรือต้องมานั่งปวดหัวกับการอ่าน Flamegraph จาก `perf` แต่ในบทความ The Hidden Bottleneck: Blocking in Async Rust (ที่ผมใช้อ้างอิง) ได้นำเสนอเครื่องมือตัวใหม่ที่ชื่อว่า `hud` ซึ่งเข้ามาเปลี่ยนเกมการ Debug ไปโดยสิ้นเชิง

ความเจ๋งของมันคือการใช้เทคโนโลยี eBPF (Extended Berkeley Packet Filter) เข้าไปเกาะติดการทำงานในระดับ Linux Kernel Scheduler โดยที่เราไม่ต้องแก้โค้ด ไม่ต้องเพิ่ม Crate หรือ Recompile โปรแกรมใหม่แม้แต่บรรทัดเดียว เพียงแค่ Attach `hud` เข้าไปที่ Process ที่กำลังรันอยู่ มันจะคอยดักจับจังหวะที่ Thread ของ Tokio ต้องรอคิวในระดับ OS นานผิดปกติ ซึ่งเป็นสัญญาณบ่งชี้ว่ามีการ Block เกิดขึ้น และแสดงผลออกมาให้เราเห็นทันที

เมื่อ `hud` ตรวจพบว่ามีความหน่วงเกิดขึ้น มันจะ Snapshot ตัว Stack Trace ณ ขณะนั้นมาแสดงให้เราดูผ่านหน้าจอ Terminal UI ที่สวยงามและเข้าใจง่าย ทำให้เราเห็นได้ทันทีว่าฟังก์ชันไหนในโค้ดของเราที่เป็นตัวการ ไม่ว่าจะเป็นการใช้ `bcrypt::hash` ที่กิน CPU นานเกินไป หรือการเผลอใช้ `std::fs` ใน Async Context เมื่อเรารู้จุดที่ชัดเจนแล้ว การแก้ไขก็ทำได้ตรงจุดดั่งการผ่าตัด เพียงแค่ย้ายงานที่เป็น Blocking เหล่านั้นออกไปรันใน `tokio::task::spawn_blocking` เพื่อแยกมันออกจาก Async Worker หลัก เพียงเท่านี้ Thread ของเราก็จะกลับมาลื่นไหล รองรับ Request ได้มหาศาลเหมือนเดิม

สิ่งที่ `hud` แสดงให้เห็นไม่ใช่แค่ความสะดวกสบายในการ Debug เท่านั้น แต่มันยังสะท้อนศักยภาพของภาษา Rust ที่สามารถเชื่อมโยงโลกของ High-level Application เข้ากับ Low-level System Programming ได้อย่างแนบเนียน การที่เราสามารถใช้เครื่องมือระดับ Kernel มาตรวจสอบ Runtime ของภาษาได้อย่างแม่นยำแบบ Zero-instrumentation นี้ คือข้อพิสูจน์ชั้นดีว่าทำไม Rust ถึงเป็นภาษาที่ทรงพลังที่สุดภาษาหนึ่งสำหรับการทำ System Software ในยุคนี้ครับ

**ข้อจำกัด** การใช้งาน `hud` ก็มีข้อจำกัดที่ควรทราบก่อนนำไปใช้จริงครับ อย่างแรกคือมันทำงานโดยวัด "อาการ" (Symptom) ของความหน่วงเป็นหลัก ดังนั้น Stack Trace ที่เราเห็นบางครั้งอาจเป็น Thread ที่ตกเป็น "เหยื่อ" (Victim) ที่ต้องรอคิว ไม่ใช่ตัวต้นเหตุที่ Block จริงๆ เสมอไป เราจึงต้องอาศัยวิจารณญาณในการวิเคราะห์แพทเทิร์นร่วมด้วยครับ

นอกจากนี้ เนื่องจากมันทำงานลึกลงไปในระดับ Kernel จึงต้องการสิทธิ์ Root และ Linux Kernel เวอร์ชัน 5.8 ขึ้นไป รวมถึงตัว Binary ของเราควรจะมี Debug Symbols อยู่ด้วยเพื่อให้แสดงชื่อฟังก์ชันได้ถูกต้อง ซึ่งถ้าโจทย์ของเราต้องการความแม่นยำระดับสูงสุดหรือต้องการเห็นสาเหตุทางตรงเป๊ะๆ เครื่องมือทางการอย่าง `tokio-console` อาจจะยังตอบโจทย์กว่า แต่สำหรับการ Triage ปัญหาหน้างานใน Production แบบเร่งด่วนโดยไม่ต้องแตะต้องโค้ด `hud` คือตัวเลือกแรกที่คุ้มค่าที่จะหยิบมาใช้ครับ
